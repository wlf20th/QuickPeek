# QuickPeek (C# / .NET 8 重构版)

原版是 AutoHotkey v2 脚本编译成的 `QuickPeek.exe`（1.3 MB）。这是用 **C# + .NET 8 + WinForms** 重写的一版，
功能对齐，重点换掉了原版最脆弱的两块：网络请求和 JSON 解析。

## 跑起来

```
bin\Debug\net8.0-windows\QuickPeek.exe      # 需要 .NET 8 桌面运行时
publish\QuickPeek.exe                        # 自包含单文件，双击即用（66 MB）
```

启动后驻留托盘：`Alt+Q` 划词、拖选/双击文字自动弹条、`Ctrl+Alt+L` 分析剪贴板、`Ctrl+Alt+S` 设置。

命令行参数（调试/集成用）：

| 参数 | 作用 |
|---|---|
| `--tray` | 静默启动（开机自启用） |
| `--settings [页码]` | 直接打开设置，可指定页（1 常规 … 5 关于） |
| `--demo "文本"` | 用给定文本弹出操作条，不抓屏 |
| `--ask "文本"` | 用第一个动作直接请求并显示结果 |
| `--sendkeys "Ctrl+C"` | 只注入一次按键，用于验证输入模拟 |

## 和 AHK 版的结构对照

| 能力 | AHK 版 | 本版 |
|---|---|---|
| HTTP 请求 | `curl.exe` 子进程 + 临时 JSON 文件 + 300ms 轮询 + 看门狗 | `HttpClient` 原生异步，无临时文件、无轮询 |
| JSON | `ExtractField(raw, '"content":"')` 手写扫描 | `System.Text.Json`，支持 `content` 数组分段、`reasoning_content` |
| 响应换行 | Edit 控件直接吃 `\n` | TextBox 只认 `\r\n`，已做归一化 |
| 全局热键 | `Hotkey()` 一行 | `RegisterHotKey` + 隐藏消息窗口 |
| 鼠标触发 | `~LButton` 钩子 | `WH_MOUSE_LL` 低级钩子，过滤自家窗口与全屏应用 |
| 按键注入 | `Send` | `SendInput`（虚拟键 + Unicode 直输，中文可打） |
| 配置 | `settings.json` | 同结构同文件名，两个版本可互换 |
| 日志 | `qp.log` | 同名同目录 |

## 过程中发现并修掉的几个真问题

1. **Alt 还按着就发 Ctrl+C** —— 热键触发的瞬间用户手指没松，注入的 `Ctrl+C` 会被目标程序理解成 `Ctrl+Alt+C`，
   复制直接失效。现在先轮询 `GetAsyncKeyState` 等修饰键物理松开，再清一遍残留，最后才发复制键。
   原 AHK 版同样存在这个隐患（表现为偶发"未捕获到选中文本"）。
2. **首次复制被吞** —— WinUI 记事本在刚结束鼠标拖选时会吞掉第一次按键。现在 700ms 没等到剪贴板就补发一次，
   实测这是拖选场景能稳定成功的必要条件。
3. **抓取阻塞 UI 线程 → 全系统鼠标卡顿** —— 抓取最多要等 2.7s（700ms + 2000ms 重试），原先跑在 UI 线程上，
   而全局鼠标钩子也装在这条线程：钩子回调被堵住，Windows 会等它，于是**整个系统的鼠标都一顿一顿**。
   现在抓取改到独立 STA 线程（剪贴板要求 STA），UI 线程全程空闲。
   实测：2.8s 的最坏抓取期间连打 80 次 `WM_NULL`，最大响应 2ms（修复前会整段超时）。
   顺带收紧了误触发：双击必须同位置、关掉操作条后 600ms 内不触发、鼠标误触发失败不弹提示。
4. **操作条不刷新** —— 第一版把"操作条可见"当成了全局抑制条件，导致不关操作条再划新词时
   钩子根本不派发，条上一直是旧文本。这是一个自己引入的回归。
   现在：划新词就地刷新内容并重新定位（点了操作条上的按钮/拖动条本身仍然不会触发抓取，
   因为按下点的窗口归属会单独判断）。
5. **抓取偶尔卡到十几秒** —— 剪贴板被别的程序占住时，单次系统调用能内部阻塞数秒，
   叠加 10 次重试会放大成 11s+，期间所有新划词都被 `_capturing` 挡掉。
   现在：整体 4s 上限，超时放弃本次（后台线程自行结束）；期间来的新划词会排队，等当前这次结束后自动补抓一次。
   慢于 1.2s 会在日志里打出各阶段耗时（备份剪贴板/发键/等剪贴板/恢复剪贴板），便于定位是谁在堵。
6. **划一次词把用户的图片/文件弄没了** —— 备份只存文本，却用 `Clipboard.Clear()` 清掉全部格式，
   还原那一步又因为备份是空串跳过。现在改成全格式快照，并且不再清空剪贴板（见前面专门一节）。

## 操作条定位

- 默认贴在**鼠标正下方居中**（让开光标箭头本身的高度），下方空间不够自动翻到上方，
  左右超出屏幕时夹紧到边界内；每次重新划词都重新定位。
- 设置里「记住拖动后的位置」只有在你**手动拖过操作条之后**才会生效。
  之前的写法只要开关打开就永远停在上次位置，看起来就是"不跟鼠标"。
- `qp.log` 每次显示都会记一行 `操作条定位: 鼠标=(x,y) 窗口=(x,y)`，定位不对时直接对着算。

## 启动与二次启动

**启动提示**用自绘气泡（`Toast.ShowNearTray`），不用托盘 `ShowBalloonTip` ——
Win11 会把 balloon 转成系统通知，标题被截断成"私密"这种莫名其妙的东西，图标也不显示。
气泡贴右下角显示 3 秒，文案带当前热键；**开机自启（`--tray`）和 `--silent` 不弹**，免得每次开机打扰。

任务栏设成自动隐藏时，工作区等于整屏，气泡会贴到屏幕最下沿、还会被弹出来的任务栏盖住 ——
所以判断到这种情况要额外往上让 64（逻辑像素）。

**二次启动**（已经在托盘里，又双击了一次 exe）：不再甩一句"已在运行"的对话框，
而是第二个进程只发一个命名事件 `Local\QuickPeek_Activate` 就退出，第一个进程收到后
把托盘菜单就地弹出来，可以直接选设置/退出。

## 另存为

结果窗底部是三个按钮：**复制结果 / 关闭 / 另存为**（也可以按 `Ctrl+S`）。

- 默认文件名 = 动作名 + 时间戳，例如 `分析日志202611141656.md`
- **扩展名跟随渲染开关**：开着 Markdown 存 `.md`，关着存 `.txt`；两种都能在对话框里手动改
- 首次打开目录是桌面，之后记住上次保存的位置；重名会提示覆盖
- UTF-8 **无 BOM**（`.md` 要进 git 或贴到别处，带 BOM 容易出隐形字符）

这里有个必须避开的坑：**保存的必须是原始文本，不能从 RichTextBox 反读**。
控件里存的是渲染后的样子 —— 表格会变成用 `─` 字符画的线、列表变成 `•`、缩进是控件属性，
反读出来写进 `.md` 就是一堆垃圾。所以 `ResultForm` 单存一份 `_raw`，渲染只影响显示。

## API Key 怎么存

`settings.json` 里**不会出现明文 key**：

- 磁盘上只有一个 `api_key_enc` 字段，内容是 `dpapi:v1:<base64>`；
- 加密用 Windows **DPAPI**（`CryptProtectData`，CurrentUser 作用域），密文绑定当前 Windows 用户，
  拷到别的机器或别的账户上解不开；
- `api_key` 字段保留但恒为空 —— 这样 AHK 版读同一个文件时不会拿到一串解不开的乱码；
- 设置界面里输入框默认是掩码，右边有「显示/隐藏」按钮；
- 旧的明文 `api_key` 会在启动时自动迁移：读出 → 加密写回 → 清空明文字段，日志里留一行 `迁移: ...`；
- 解不开时（换了机器/用户）当空值处理，日志提示重填，不会带着坏 key 去请求。

只用两个 `crypt32` 导出函数，没有引 NuGet 包，也不影响单文件体积。

## 结果窗的 Markdown 渲染

模型基本都在回 Markdown，纯文本贴进 TextBox 会连 `**`、`|` 一起显示。现在按 Markdown 排版：
标题、粗体/斜体/删除线、行内代码、代码块、列表、引用、分隔线、表格都能认。
设置 → 常规 → 结果窗里有「渲染 Markdown」开关，格式乱掉时可以关掉退回纯文本。

**实现方式：生成 RTF 一次性赋值，不是逐段调 `SelectionFont`。**

第一版用的是 `AppendText` + `SelectionFont`/`SelectionColor` 逐个 token 上色，
20KB 的回答要 **9968ms**（每次 Select 都触发 RichEdit 重排）。改成拼 RTF 字符串再
`rtb.Rtf = ...`，同样的内容 **114ms**，快了 87 倍；日常 700 字左右 30ms 以内。

几个踩过的坑，都写在代码注释里了：

- **中文要走 `\uN?`**，且 N 是**有符号** 16 位（超过 32767 要减 65536），否则 emoji 和部分汉字会乱码
- **行内代码的底色必须显式设置**，用 `SelectionBackColor` 时留空会继承上一个字符的底色，
  于是行内代码后面的普通文字会莫名带上灰底
- **表格对齐不能按"中文算 2 个宽度"估算**：Consolas 下中文是回退字体渲染的，实际宽度不是 2 倍，
  只能用 `TextRenderer.MeasureText` 实测再换算成 RTF 制表位。而且 RichEdit 把 twips 按 96dpi 折算，
  测量结果要先除回 DPI 缩放系数，否则 150% 缩放下列会偏 1.5 倍
- **反斜杠不做 Markdown 转义折叠**：CommonMark 里 `\\` 表示一个 `\`，但看日志的场合
  Windows 路径和正则里的反斜杠必须原样保留，吃掉一层比多显示一层糟得多
- **空段落等于一整行高**：段间距用 `\sa` 控制，不要用空行凑，否则段与段之间会空出两大截
- `\brdrb` 段落边框在 WinForms 的 RichEdit 里**不生效**，表格分隔线最后是用字符线画的

代码块围栏支持 ` ``` ` 和 `~~~`；`~~~` 是不少模型的习惯写法，只认前者会整块当正文显示。

## 终端里怎么判断"有没有选中文字"

**问题**：在跑着 llama-server / 构建 / 批处理的 cmd 或 Windows Terminal 里随便拖一下，
正在跑的东西就被 Ctrl+C 打断了（`Terminate batch job (Y/N)?`）。

**原因**：终端对"Ctrl+Shift+字母"的输入编码会忽略 Shift，直接按 Ctrl+字母 发出去。
于是 `Ctrl+Shift+C` 的语义完全取决于有没有选区：**有选区是复制，没选区就是 `0x03` = SIGINT**。
而鼠标误触发（拖窗口、拖空白区）恰恰就是"没有选区"的情况。

**解法：先问清楚，再决定发不发键。** 用 UI Automation 的 `TextPattern` 直接问终端：

- `GetSelection()` 拿到的文字非空 → **有选区**
- 终端支持选区概念但取回的是空/全空白 → **没有选区**
- 该窗口没有可用的文本接口 → **未知**

于是行为和 cmd 自己的 Ctrl+C 完全一致：

| 场景 | 行为 |
|---|---|
| 终端里有选中文字 | 直接把 UIA 里的文字当结果（**一个键都不发**，零打断风险），弹操作条 |
| 终端里没选中 | 什么都不做，日志记一句 `当前没有选中文字，不做任何动作` |
| 探不出来（没有 UIA 文本接口的终端） | 鼠标触发一律不发键；只有 `Alt+Q` 热键才按老路子发一次复制键 |

WT 的 `TermControl` 和 conhost 的屏幕缓冲区都实现了 TextPattern，`GetSelection()` 在拖选过程中
逐字实时更新（见 `tools/uiaprobe --watch`），拿到的就是用户眼前那几行。
唯一的坑是 UIA 会把多行选区中间的行右侧补齐到整屏宽度，所以取回后要按行 `TrimEnd`。

## 普通程序里也先问一句（"没选中就别发键"）

同一套探针不止终端用。以前在任意程序里拖一下（拖滑块、拖面板、拖图片）都会：

- 清空剪贴板 → 发 `Ctrl+C` → 等 700ms → 再补发一次 → 再等 2 秒，**最长 2.7 秒**才放弃；
- 如果这个程序"没选中时 Ctrl+C 也有行为"（VS Code 复制整个当前行、部分编辑器复制当前段落），
  还会弹出一条内容跟选区毫无关系的操作条。

现在普通程序也先问探针，只有三种结论会影响行为：

| 探针结论 | 行为 |
|---|---|
| 有选区（可信） | 照常发复制键，但超时收紧到 900ms + 900ms |
| **没选区（可信）** | **直接返回**：不发键、不碰剪贴板、不弹条 |
| 探不出来 | 走老逻辑（700ms + 2000ms，保留补发） |

**为什么只问"焦点链路"而不是遍历整窗**：`AutomationElement.FocusedElement` 往上最多 8 层找第一个
支持 TextPattern 的控件，实测 60–75ms；遍历整窗在浏览器/IDE 里是几百毫秒起，每次都付不起。
副作用还是好的：侧栏里"上次选中的文件/列表项"不会被误当成用户选区。

三道保险，避免问错人：

1. **焦点元素必须属于目标窗口的进程**（WinUI 的顶层元素 `NativeWindowHandle` 常是 0，
   靠祖先 hwnd 判断会一路走到桌面，所以用 pid）；
2. **只信文本面板类控件**（`Document` / `Text` / `Edit`）—— 焦点落在按钮、菜单上就直接算"探不出来"；
3. **有选区时不用 UIA 的文字**，只让它当"有没有"的裁判，正文仍然从剪贴板取（质量最稳）；
   只有终端那条路径才直接采用 UIA 文本。

诊断命令：`QuickPeek.exe --probe [窗口句柄]`，把当前焦点窗口的探针结论写进 `qp.log`。


**另外两层保护**：

1. **拖标题栏不算划词**：按下时用 `GetTitleBarInfo` 取真实标题栏矩形，落在里面直接忽略。
   之前只看位移，拖着窗口满屏跑也会触发抓取，这是误触发的主要来源。
2. **终端里发复制键只发一次、失败不补发**（补发等于再捅一刀）。

验证脚本：`tools/test_terminal.py`（误触发不打断 bat）、`tools/uiaprobe/`（独立 UIA 探针小工程）。

## "选中即复制"快路径（第三方 SSH 客户端）

终端白名单是按进程名硬编码的，永远会漏 —— 比如 `NyaTerm.exe`（FinalShell 系）就不在名单里，
于是它走了默认的 `Ctrl+C`，一样是 0x03，一样打断远端命令。加名单治不了根。

真正的解法是**别急着发键**：不少终端/SSH 客户端是"选中即复制"，拖选松手时自己就把内容写进剪贴板了。
所以鼠标按下时先记下 `GetClipboardSequenceNumber()`，抓取开始时先比一次：

- **序列号变了** → 应用已经复制好了，直接读剪贴板出条，**一个键都不发**。
  这条路径还顺带解决了一个隐患：以前无条件先清空剪贴板，会把这部分刚复制好的内容清掉。
- **序列号没变** → 才发一次复制键（SSH 客户端只发一次、不补发）。

另外把"等剪贴板"从轮询 `GetText` 改成**先等序列号变化、变了再读文本**。
Java 写的终端在响应剪贴板请求时可能慢上半秒以上，直接轮询 `GetText` 会一路异常到底；
而且以前超时那一刻即使剪贴板里已经有内容（日志里那句"剪贴板长度=314"），也照样丢弃 —— 现在是先收下再说。

验证脚本 `tools/test_autocopy.py`：拖选过程中人为往剪贴板写一段标记文本，观察日志是否出现
`应用已自动复制(N 字)，未发送任何按键`，并确认剪贴板内容没有被清空。

## 剪贴板备份：图片、文件、富文本都要原样还回去

老流程是"备份文本 → `Clipboard.Clear()` → 发复制键 → 只把文本写回去"。问题在于
`Clipboard.Clear()` 清的是**所有格式**，而备份只存了文本：

- 复制了一个文件/一张截图/一段 HTML 富文本，然后随手划个词 → 原内容在 `Clear()` 那一步就没了；
- 还原时判断是 `if (backup != "")`，备份为空串就直接跳过，连写回都没有；
- 实测：剪贴板里只放 `HTML Format`，在记事本空白处拖 40px（无选区），结束后只剩
  `DataObject` / `Ole Private Data` 两个空壳。

现在拆成两处改动：

**1. 备份换成全格式快照（`ClipboardSnapshot`）**

用 Win32 枚举 `EnumClipboardFormats` 并逐个深拷贝，不再依赖 `GetText`：

| 格式类型 | 处理方式 |
|---|---|
| 绝大多数（`CF_TEXT`/`CF_UNICODETEXT`/`CF_DIB`/`CF_DIBV5`/`CF_HDROP`/`CF_LOCALE`/`HTML Format`/`Rich Text Format`/`PNG`…） | 都是 HGLOBAL，`GlobalSize` + 整块 `RtlMoveMemory` 复制 |
| `CF_BITMAP` / `CF_PALETTE` | GDI 句柄，`CopyImage` / `CreatePalette` 克隆 |
| `CF_METAFILEPICT` / `CF_ENHMETAFILE` | 结构体里还挂着 `HMETAFILE`，连内部句柄一起 `CopyMetaFile` / `CopyEnhMetaFile` |
| `CF_OWNERDISPLAY`、`CF_DSP*`、`CF_GDIOBJ*`、`CF_PRIVATEFIRST..LAST` | 合成/私有格式，数据由原窗口自己渲染，跨进程本来就克隆不了，跳过并记日志 |
| `DataObject` / `Ole Private Data` | OLE 内部结构，跨进程写回只会让别的程序拿到野指针，跳过 |

`SetClipboardData` 成功后句柄归系统所有，代码里立刻把引用置 0，避免二次释放；
还原失败（被别的程序抢走）的项则自己 `GlobalFree` / `DeleteObject`，不泄漏。

**2. 不再清空剪贴板，"复制有没有落地"改看序列号**

发键前记下 `GetClipboardSequenceNumber()`，只有应用真的写过剪贴板它才会变。带来两个好处：

- 超时放弃时用户剪贴板**一动都没动过**，连还原都不需要；
- 但反过来，超时后"再看一眼剪贴板"这个兜底必须先确认序列号变过 —— 否则读到的是
  用户原本就有的内容（上一段文本、图片的伴生文本），会被当成选区弹出去。

还原只在"序列号确实变过"时执行：抓取成功（把选区文本换回原内容），或复制了非文本内容
（读不出文本）。空快照就是原本空剪贴板，`EmptyClipboard` 一下即完成还原。

**验证**（两个脚本都是真机跑）：

- `tools/test_snapshot.py` 调 `QuickPeek.exe --snaptest` 做自检：纯文本 / 文件 / 图片
  （`CF_DIB`+`CF_BITMAP`+`CF_DIBV5` 三格式）/ HTML / RTF / 文本+HTML 混合，**6 项全部格式与内容一致**；
- `tools/test_preserve_hotkey.py` 走真实抓取链路：剪贴板里放文件、图片、HTML，各按一次 Alt+Q
  （日志 `抓取成功: 35 字, 耗时 15x ms`，是完整的"备份→发键→还原"），结束后格式和内容原样；
- 无选区场景序列号 `894 → 894`，剪贴板完全没被碰过。

## 取舍（说实话的部分）

- **体积**：1.3 MB → 66 MB。自包含单文件把 .NET 运行时打进去了，WinForms 不支持裁剪（`NETSDK1175`），
  要小就只能框架依赖（~1.5 MB），但那台机器必须预装 .NET 8 桌面运行时。
  另外"读终端选区"用了 UI Automation，它属于 WindowsDesktop 的 WPF profile，会把整套 WPF 拖进发布产物
  （不压缩 137 MB），所以发布时开 `EnableCompressionInSingleFile` 压回 66 MB。
  另外必须带 `IncludeNativeLibrariesForSelfExtract`：WPF 的 `OSVersionHelper` 启动时要真去
  `LoadLibrary` 一个原生 DLL，纯打包模式里加载不到，UIA 会在第一次调用时抛
  `TypeInitializationException`（见下节）。原生库解压到 `%TEMP%\.net\`，一次性，之后启动仍是 ~0.3s。
- **启动**：约 0.3 秒；压缩版**首次**运行约 1.3 秒（解压 + 杀软扫描），之后稳定在 0.3 秒。常驻托盘所以只付一次。
- **DX 提升**：强类型 + 编译期检查 + 断点调试，比在 1300 行 AHK 里读 `qp.log` 舒服得多。
- **代价**：hotkey/剪贴板/窗口定位这些 Win32 活儿，AHK 一行能做的事这里要 P/Invoke。

## 图标

`app.ico` 由 `tools/make_icon.py` 生成（纯 Pillow 画，没有外部素材）：蓝紫渐变圆角底 + 白色的放大镜。

- 多尺寸 **16/20/24/32/40/48/64/128/256** 全部内嵌，代码按目标尺寸自动挑帧
  （托盘在 150% 缩放下要的是 24px，不是 16px，取错会被拉伸糊掉）
- **小尺寸是简化版**：16–40px 只有放大镜，48px 以上才在镜片里加文字光标。
  最初的版本所有尺寸都画 3 行文字，结果 16px 糊成一个"⊖"，看着像禁止/缩小图标
- 三处复用同一份资源：exe 文件图标（`ApplicationIcon`）、托盘（`AppIcon.Tray`）、窗口标题栏（`AppIcon.Window`）

改图标：`python tools/make_icon.py` → 看 `tools/preview.png`（深色/浅色底各一排）→ 重新发布。

## 已知可继续改进

- 流式输出（现在是整段返回，长回答要等）
- 请求进行中再按热键只会提示"稍等"，没有取消按钮
- 多显示器不同 DPI 时，操作条按创建时的屏幕 DPI 布局，跨屏拖动后不会重新缩放
- Markdown 渲染不处理嵌套（`**加粗里的 \`代码\`**` 只会有粗体）、图片、HTML 和链接跳转
- 终端划词的 conhost 分支只在 WT 上实测过；经典 conhost 窗口的 UIA 表现还没验证
  （探不出来时会退回"鼠标不抓、热键才抓"的保守行为，不会打断命令）
- 普通程序的探针在 WT 和记事本上实测过（有选区读得到、"没选中"能正确否决）；
  浏览器/Electron（Chrome、Typora 一类）没有跑到干净的验证环境，机制相同但未实测
- 焦点落在右键菜单/输入法候选框上时探针会判"未知"，退回老路径（多等一轮复制超时）——
  这是有意的保守，不能拿菜单的"选区"当用户选区
- 抓取超时被放弃后，那个后台线程仍会跑完并按需还原剪贴板；若紧接着又做了一次抓取，两者可能互相覆盖剪贴板
  （概率低，且最终内容一般是用户原本的剪贴板）
- 抓取等待期间（探针 Unknown 时最长约 2.9s）如果用户自己复制了别的内容，收尾的还原会把那次复制覆盖掉。
  想彻底避免得记住"这次复制之后"的序列号，但那又和应用延迟渲染的时序纠缠在一起，暂时没做
- 全局鼠标钩子仍装在 UI 线程，若将来 UI 线程出现长阻塞，钩子还会被拖住；彻底方案是把钩子放到独立消息循环线程
