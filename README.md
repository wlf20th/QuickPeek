# QuickPeek (C# / .NET 8 重构版)

原版是 AutoHotkey v2 脚本编译成的 `QuickPeek.exe`（1.3 MB）。这是用 **C# + .NET 8 + WinForms** 重写的一版，
功能对齐，重点换掉了原版最脆弱的两块：网络请求和 JSON 解析。

## 跑起来

```
bin\Debug\net8.0-windows\QuickPeek.exe      # 需要 .NET 8 桌面运行时
publish\QuickPeek.exe                        # 自包含单文件，双击即用（63 MB）
```

启动后驻留托盘：`Alt+Q` 划词、拖选/双击文字自动弹条、`Ctrl+Alt+L` 分析剪贴板、`Ctrl+Alt+S` 设置。

命令行参数（调试/集成用）：

| 参数 | 作用 |
|---|---|
| `--tray` | 静默启动（开机自启用） |
| `--settings [页码]` | 直接打开设置，可指定页（1 常规 … 5 关于） |
| `--demo "文本"` | 用给定文本弹出操作条，不抓屏 |
| `--ask "文本"` | 用第一个动作直接请求并显示结果 |
| `--sendkeys "Ctrl+C"` | 只注入一次按键，用于验证输入模拟 |

## 和 AHK 版的结构对照

| 能力 | AHK 版 | 本版 |
|---|---|---|
| HTTP 请求 | `curl.exe` 子进程 + 临时 JSON 文件 + 300ms 轮询 + 看门狗 | `HttpClient` 原生异步，无临时文件、无轮询 |
| JSON | `ExtractField(raw, '"content":"')` 手写扫描 | `System.Text.Json`，支持 `content` 数组分段、`reasoning_content` |
| 响应换行 | Edit 控件直接吃 `\n` | TextBox 只认 `\r\n`，已做归一化 |
| 全局热键 | `Hotkey()` 一行 | `RegisterHotKey` + 隐藏消息窗口 |
| 鼠标触发 | `~LButton` 钩子 | `WH_MOUSE_LL` 低级钩子，过滤自家窗口与全屏应用 |
| 按键注入 | `Send` | `SendInput`（虚拟键 + Unicode 直输，中文可打） |
| 配置 | `settings.json` | 同结构同文件名，两个版本可互换 |
| 日志 | `qp.log` | 同名同目录 |

## 过程中发现并修掉的五个真问题

1. **Alt 还按着就发 Ctrl+C** —— 热键触发的瞬间用户手指没松，注入的 `Ctrl+C` 会被目标程序理解成 `Ctrl+Alt+C`，
   复制直接失效。现在先轮询 `GetAsyncKeyState` 等修饰键物理松开，再清一遍残留，最后才发复制键。
   原 AHK 版同样存在这个隐患（表现为偶发"未捕获到选中文本"）。
2. **首次复制被吞** —— WinUI 记事本在刚结束鼠标拖选时会吞掉第一次按键。现在 700ms 没等到剪贴板就补发一次，
   实测这是拖选场景能稳定成功的必要条件。
3. **抓取阻塞 UI 线程 → 全系统鼠标卡顿** —— 抓取最多要等 2.7s（700ms + 2000ms 重试），原先跑在 UI 线程上，
   而全局鼠标钩子也装在这条线程：钩子回调被堵住，Windows 会等它，于是**整个系统的鼠标都一顿一顿**。
   现在抓取改到独立 STA 线程（剪贴板要求 STA），UI 线程全程空闲。
   实测：2.8s 的最坏抓取期间连打 80 次 `WM_NULL`，最大响应 2ms（修复前会整段超时）。
   顺带收紧了误触发：双击必须同位置、关掉操作条后 600ms 内不触发、鼠标误触发失败不弹提示。
4. **操作条不刷新** —— 第一版把"操作条可见"当成了全局抑制条件，导致不关操作条再划新词时
   钩子根本不派发，条上一直是旧文本。这是一个自己引入的回归。
   现在：划新词就地刷新内容并重新定位（点了操作条上的按钮/拖动条本身仍然不会触发抓取，
   因为按下点的窗口归属会单独判断）。
5. **抓取偶尔卡到十几秒** —— 剪贴板被别的程序占住时，单次系统调用能内部阻塞数秒，
   叠加 10 次重试会放大成 11s+，期间所有新划词都被 `_capturing` 挡掉。
   现在：整体 4s 上限，超时放弃本次（后台线程自行结束）；期间来的新划词会排队，等当前这次结束后自动补抓一次。
   慢于 1.2s 会在日志里打出各阶段耗时（读取备份/清空/发键/等剪贴板/恢复），便于定位是谁在堵。

## 操作条定位

- 默认贴在**鼠标正下方居中**（让开光标箭头本身的高度），下方空间不够自动翻到上方，
  左右超出屏幕时夹紧到边界内；每次重新划词都重新定位。
- 设置里「记住拖动后的位置」只有在你**手动拖过操作条之后**才会生效。
  之前的写法只要开关打开就永远停在上次位置，看起来就是"不跟鼠标"。
- `qp.log` 每次显示都会记一行 `操作条定位: 鼠标=(x,y) 窗口=(x,y)`，定位不对时直接对着算。

## 结果窗的 Markdown 渲染

模型基本都在回 Markdown，纯文本贴进 TextBox 会连 `**`、`|` 一起显示。现在按 Markdown 排版：
标题、粗体/斜体/删除线、行内代码、代码块、列表、引用、分隔线、表格都能认。
设置 → 常规 → 结果窗里有「渲染 Markdown」开关，格式乱掉时可以关掉退回纯文本。

**实现方式：生成 RTF 一次性赋值，不是逐段调 `SelectionFont`。**

第一版用的是 `AppendText` + `SelectionFont`/`SelectionColor` 逐个 token 上色，
20KB 的回答要 **9968ms**（每次 Select 都触发 RichEdit 重排）。改成拼 RTF 字符串再
`rtb.Rtf = ...`，同样的内容 **114ms**，快了 87 倍；日常 700 字左右 30ms 以内。

几个踩过的坑，都写在代码注释里了：

- **中文要走 `\uN?`**，且 N 是**有符号** 16 位（超过 32767 要减 65536），否则 emoji 和部分汉字会乱码
- **行内代码的底色必须显式设置**，用 `SelectionBackColor` 时留空会继承上一个字符的底色，
  于是行内代码后面的普通文字会莫名带上灰底
- **表格对齐不能按"中文算 2 个宽度"估算**：Consolas 下中文是回退字体渲染的，实际宽度不是 2 倍，
  只能用 `TextRenderer.MeasureText` 实测再换算成 RTF 制表位。而且 RichEdit 把 twips 按 96dpi 折算，
  测量结果要先除回 DPI 缩放系数，否则 150% 缩放下列会偏 1.5 倍
- **反斜杠不做 Markdown 转义折叠**：CommonMark 里 `\\` 表示一个 `\`，但看日志的场合
  Windows 路径和正则里的反斜杠必须原样保留，吃掉一层比多显示一层糟得多
- **空段落等于一整行高**：段间距用 `\sa` 控制，不要用空行凑，否则段与段之间会空出两大截
- `\brdrb` 段落边框在 WinForms 的 RichEdit 里**不生效**，表格分隔线最后是用字符线画的

代码块围栏支持 ` ``` ` 和 `~~~`；`~~~` 是不少模型的习惯写法，只认前者会整块当正文显示。

## 终端里为什么不自动抓取

**问题**：在跑着 llama-server / 构建 / 批处理的 cmd 或 Windows Terminal 里随便拖一下，
正在跑的东西就被 Ctrl+C 打断了（`Terminate batch job (Y/N)?`）。

**原因**：终端对"Ctrl+Shift+字母"的输入编码会忽略 Shift，直接按 Ctrl+字母 发出去。
所以当终端里**没有选区**时，我们发的 `Ctrl+Shift+C` 被编码成 `0x03` 送到 shell，那就是 SIGINT ——
命令行程序收到立刻中断，批处理弹 `Terminate batch job`。而鼠标误触发（拖标题栏、拖一下窗口）
恰恰就是"没有选区"的情况。

**处理**（两层）：

1. **拖标题栏不再算划词**：按下时用 `GetTitleBarInfo` 取真实标题栏矩形，落在里面直接忽略。
   之前只看位移，拖着窗口满屏跑也会触发抓取，这是误触发的主要来源。
2. **终端里鼠标触发一律不发键**：识别 WindowsTerminal / conhost / cmd / pwsh / mintty 等，
   命中就只记日志（首次还会提示一句），一个键都不发。终端里要抓取请**先用鼠标选中文字，再按 Alt+Q**。
   热键路径是用户主动动作，仍然发 `Ctrl+Shift+C`，但**只发一次、失败不补发**（补发会再来一次 0x03）。

验证脚本 `tools/test_bat_safe.py`：起一个每秒写日志的 bat，然后拖标题栏、拖空白区、点窗口内部，
看 bat 是否还在写。修复后三个场景全部仍在跑；修复前这三下都会把 bat 打断。

## "选中即复制"快路径（第三方 SSH 客户端）

终端白名单是按进程名硬编码的，永远会漏 —— 比如 `NyaTerm.exe`（FinalShell 系）就不在名单里，
于是它走了默认的 `Ctrl+C`，一样是 0x03，一样打断远端命令。加名单治不了根。

真正的解法是**别急着发键**：不少终端/SSH 客户端是"选中即复制"，拖选松手时自己就把内容写进剪贴板了。
所以鼠标按下时先记下 `GetClipboardSequenceNumber()`，抓取开始时先比一次：

- **序列号变了** → 应用已经复制好了，直接读剪贴板出条，**一个键都不发**。
  这条路径还顺带解决了一个隐患：以前无条件先清空剪贴板，会把这部分刚复制好的内容清掉。
- **序列号没变** → 才发一次复制键（SSH 客户端只发一次、不补发）。

另外把"等剪贴板"从轮询 `GetText` 改成**先等序列号变化、变了再读文本**。
Java 写的终端在响应剪贴板请求时可能慢上半秒以上，直接轮询 `GetText` 会一路异常到底；
而且以前超时那一刻即使剪贴板里已经有内容（日志里那句"剪贴板长度=314"），也照样丢弃 —— 现在是先收下再说。

验证脚本 `tools/test_autocopy.py`：拖选过程中人为往剪贴板写一段标记文本，观察日志是否出现
`应用已自动复制(N 字)，未发送任何按键`，并确认剪贴板内容没有被清空。

## 取舍（说实话的部分）

- **体积**：1.3 MB → 63 MB。自包含单文件把 .NET 运行时打进去了，WinForms 不支持裁剪（`NETSDK1175`），
  要小就只能框架依赖（~1.5 MB），但那台机器必须预装 .NET 8 桌面运行时。
- **启动**：冷启动从毫秒级变成约 0.3–0.5 秒（单文件还要解压运行时）。常驻托盘所以只付一次。
- **DX 提升**：强类型 + 编译期检查 + 断点调试，比在 1300 行 AHK 里读 `qp.log` 舒服得多。
- **代价**：hotkey/剪贴板/窗口定位这些 Win32 活儿，AHK 一行能做的事这里要 P/Invoke。

## 图标

`app.ico` 由 `tools/make_icon.py` 生成（纯 Pillow 画，没有外部素材）：蓝紫渐变圆角底 + 白色的放大镜。

- 多尺寸 **16/20/24/32/40/48/64/128/256** 全部内嵌，代码按目标尺寸自动挑帧
  （托盘在 150% 缩放下要的是 24px，不是 16px，取错会被拉伸糊掉）
- **小尺寸是简化版**：16–40px 只有放大镜，48px 以上才在镜片里加文字光标。
  最初的版本所有尺寸都画 3 行文字，结果 16px 糊成一个"⊖"，看着像禁止/缩小图标
- 三处复用同一份资源：exe 文件图标（`ApplicationIcon`）、托盘（`AppIcon.Tray`）、窗口标题栏（`AppIcon.Window`）

改图标：`python tools/make_icon.py` → 看 `tools/preview.png`（深色/浅色底各一排）→ 重新发布。

## 已知可继续改进

- 流式输出（现在是整段返回，长回答要等）
- 请求进行中再按热键只会提示"稍等"，没有取消按钮
- 多显示器不同 DPI 时，操作条按创建时的屏幕 DPI 布局，跨屏拖动后不会重新缩放
- Markdown 渲染不处理嵌套（`**加粗里的 \`代码\`**` 只会有粗体）、图片、HTML 和链接跳转
- 终端里鼠标划词被主动禁用（避免打断命令），只能选中后按热键。要恢复得先解决
  "如何判断终端里到底有没有选区"，目前没找到可靠办法（WT 不暴露选区，注入的拖动也建不了选区）
- 抓取超时被放弃后，那个后台线程仍会跑完并恢复剪贴板；若紧接着又做了一次抓取，两者可能互相覆盖剪贴板
  （概率低，且最终内容一般是用户原本的剪贴板）
- 全局鼠标钩子仍装在 UI 线程，若将来 UI 线程出现长阻塞，钩子还会被拖住；彻底方案是把钩子放到独立消息循环线程
